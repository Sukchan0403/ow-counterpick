# 오버워치 밴프준 영웅 추천 서비스 — MVP 설계

- 작성일: 2026-09-07
- 상태: 설계 승인 완료 (Cowork 화면 목업 작업으로 인계 예정)

## 배경 및 목표

게임 중(또는 밴/픽 단계에서) 상대 조합, 우리 조합, 맵을 종합적으로 고려해
빈 포지션에 어울리는 영웅을 추천해주는 웹서비스를 만든다. 실제 플레이
중에는 이성적으로 조합을 판단하기 어려운 경우가 많은데, 이 판단을
도와주는 것이 목표다. 개인 포트폴리오 프로젝트.

> 이전에 논의한 "오버워치 전적 검색(OP.GG 스타일)" 프로젝트는 이
> 프로젝트로 **대체**한다. 기존 스펙/구현 계획 문서는 폐기했다.

전체 구상에는 아래 2가지 사용 시나리오가 있었으나, 첫 버전(MVP)은
1번에 집중한다.

1. **실시간 밴프준 보조 (본 스펙의 범위)** — 게임 중 상대/우리 조합과
   맵을 입력하면 빈 포지션에 어울리는 영웅을 추천
2. 사전 드래프트 시뮬레이션 (추후 별도 스펙) — 게임 전 양 팀 조합을
   미리 입력해보며 연습/분석하는 도구

## 핵심 제약: 추천 데이터의 출처

오버워치는 공식 매치 통계 API가 없어 실시간으로 승률 기반 카운터/시너지
데이터를 가져올 수 없다. 따라서:

- 카운터/시너지/맵별 영웅 평가 데이터는 **개발 단계에서** 웹검색과
  커뮤니티 자료(승률 통계 사이트, 커뮤니티 여론)를 조사해 미리
  큐레이션한 시드 데이터로 구축한다.
- 서비스 런타임에는 외부 API를 호출하지 않는다 — 자체 DB(SQLite)만
  조회한다. 빠르고 안정적이며 비용이 들지 않는다.
- 모든 영웅×영웅, 영웅×맵 조합을 다 채우지는 않는다. 잘 알려진
  카운터/시너지 관계 위주로 시작하고, 데이터가 없는 조합은 중립
  점수로 처리한다. 이후 필요에 따라 데이터를 늘려간다.
- 메타가 바뀌면 시드 데이터를 수동으로 갱신해야 한다 (실시간 자동
  갱신 없음 — 향후 확장 항목).

### 결측치 3단 상태 (아키텍처 결정)

"데이터 없는 조합은 중립 점수"라는 규칙만으로는 "아직 검토 안 한 조합"과
"검토했는데 실제로 중립인 조합"을 구분할 수 없어 추천의 신뢰도를 깎아먹는다.
그래서 결측치를 3단 상태로 명시적으로 구분한다.

| 상태 | 의미 | 근거 목록 노출 |
|---|---|---|
| 미검토 | 아직 조사 안 함 | "데이터 없음" 배지 표시 |
| 검토완료-중립 | 조사했으나 유의미한 관계 없음 | 배지 없음 (조용히 0점 처리) |
| 검토완료-값있음 | 조사 결과 실제 관계 있음 | 기존처럼 점수+근거 표시 |

**구현 방식**

- `counter_relations`/`synergy_relations`는 원래 "관계가 있는 것만"
  저장하는 테이블이라 "검토완료-중립"을 표현할 자리가 없다. 가벼운
  마커 테이블 `reviewed_neutral_pairs(hero_id, other_hero_id,
  relation_type)`를 추가해, 두 관계 테이블에도 이 마커 테이블에도
  없으면 "미검토", 마커 테이블에만 있으면 "검토완료-중립", 관계
  테이블에 있으면 "검토완료-값있음"으로 판정한다.
- `map_hero_ratings`는 이미 `rating`에 "보통"이 있으므로 새 테이블
  없이, **큐레이션 시 "보통"도 건너뛰지 않고 명시적으로 행을
  기록하는 운영 규칙**만 지키면 된다 (행이 아예 없으면 미검토).
- API 응답에 `data_gaps: string[]` 필드를 추가한다 — "미검토" 상태인
  항목만 여기 담는다 (기존 `reasons`/`notes`와는 성격이 달라 분리).
  이 상태를 보여줄 화면 목업은 아직 없어 별도로 필요하다.

**구현 범위 관련 주의 (2026-09-08, 최종 리뷰 반영)**: 이 절은 카운터/시너지/맵
3개 차원 모두에 3단 상태를 적용하는 것으로 서술돼 있지만, 실제로는
**카운터·시너지 두 차원만 구현됐다.** `data_gaps`는 `backend/app/scoring.py`에서
카운터/시너지 미검토 조합만 채우고, 맵 차원(`map_hero_ratings`)은 여전히
"데이터 없으면(또는 '보통'이면) 그냥 0점"인 기존 2단(중립 vs 값있음) 처리
그대로다 — 맵 이름을 라우터에서 `scoring.py`까지 넘기는 배관과 그에 맞는
테스트가 아직 없어서다. 맵 차원의 3단 상태 구현은 향후 과제로 남겨둔다.

**보류한 대안: 태그+룰 기반 스코어링 엔진**

영웅에 태그(사거리/CC/기동성/안티실드 등)를 붙이고 소수의 룰로 자동
채점하는 방식도 검토했다. 신규 영웅 추가 비용이 줄고 근거가 게임
메커니즘에 기반해 설득력이 있다는 장점이 있지만, MVP 대비 설계·구현
범위가 크게 늘어난다(태그 스키마, 룰 테이블, 예외 테이블, 맵/조합
아키타입 판정까지 필요). **채택하지 않고 보류한다.** 대신:

- 지금은 3개 테이블(`counter_relations`/`synergy_relations`/
  `map_hero_ratings`) 구조를 유지하고 수동 큐레이션을 계속한다.
- 큐레이션할 때 참고용 체크리스트(코드화하지 않음)로만 활용한다 —
  예: "후보가 CC 보유 + 상대가 고기동·CC비면역인가", "후보가 안티실드
  + 상대가 실드 보유인가" 같은 질문을 스스로 던져 일관성을 높인다.
- **전환 트리거**: 페어와이즈 데이터가 100개 이상 쌓이고 반복되는
  패턴이 뚜렷이 보이면, 그때 5~8개 정도의 핵심 룰부터 실험적으로
  런타임에 도입하는 것을 재검토한다.

## 아키텍처

```
[Next.js 프론트엔드] → [FastAPI 백엔드] → [SQLite: 큐레이션된 카운터/시너지/맵 데이터]
```

외부 API 의존이 없어 이전에 검토했던 "전적 검색" 프로젝트보다 오히려
더 단순한 구조다. 프론트엔드는 Vercel, 백엔드는 Render/Railway 등에
배포하는 걸 가정한다.

**폴더 구조**: 5주차에 백엔드/프론트엔드를 각각 별도 Docker 컨테이너로
분리할 예정이므로, 모든 백엔드(FastAPI) 코드는 반드시 `backend/` 폴더
안에 스캐폴딩한다 (프론트엔드는 `frontend/`).

## 컴포넌트

### 프론트엔드 (Next.js)

- **입력 폼**
  - 상대 팀 픽 영웅 (최대 5명, 검색 가능한 선택 UI)
  - 우리 팀 픽 영웅 (포지션 태그 포함, 최대 4명)
  - 채워야 할 빈 포지션 (탱커 / 딜러 / 힐러 중 선택)
  - 맵 (드롭다운, 개별 맵 이름 단위 — 약 20여 개)
- **결과 화면**
  - 추천 영웅 순위 리스트 (상위 3~5개)
  - 각 항목마다 점수와 함께 간단한 근거 텍스트 표시 (예: "상대 겐지를
    카운터함", "우리 팀 레킹볼과 시너지 좋음", "이 맵에서 강세")

### 백엔드 (FastAPI)

- `POST /api/recommendations`
  - 입력: 상대 팀 영웅 목록, 우리 팀 영웅 목록, 채울 포지션, 맵
  - 처리: 해당 포지션의 모든 영웅을 후보로 놓고 각각 점수 계산
    (아래 "점수 계산 로직" 참조) 후 내림차순 정렬
  - 출력: 순위 리스트 (영웅명, 총점, 근거 목록)
- `GET /api/heroes` — 프론트 입력 폼의 영웅 선택 목록용
- `GET /api/maps` — 프론트 입력 폼의 맵 선택 목록용

**점수 계산 로직**

후보 영웅 X에 대해:

- **카운터 점수**: X가 카운터하는 상대 팀 영웅 수 × 가중치 **−** 오히려 X를
  카운터하는 것으로 알려진 상대 팀 영웅 수 × 같은 크기의 가중치(2026-09-15
  추가). `counter_relations`는 방향성이 있는 테이블이라 "X가 상대를 카운터함"과
  "상대가 X를 카운터함"은 별개 행이며 둘 다 알려질 수 있다 — 실사용 중 D.Va가
  자신을 카운터하는 상대(시메트라·에코)를 상대로도 "미검토"로 잘못 표시되는
  문제가 발견되어, 반대 방향 관계도 (a) 감점으로 반영하고 (b) "검토된 관계"로
  쳐서 `data_gaps`에서 빠지도록 고쳤다.
- **시너지 점수**: X와 시너지가 좋은 우리 팀 영웅 수 × 가중치
- **맵 점수**: 해당 맵에서 X의 평가(강함/보통/약함)에 따른 가중치
- 총점 = 네 항목의 합, 총점 기준 내림차순 정렬

데이터가 없는 조합은 "결측치 3단 상태"에 따라 처리한다 — "검토완료-중립"은
조용히 0점, "미검토"는 0점 처리하되 `data_gaps`에 노출한다. 카운터 관계는
반대 방향으로만 알려져 있어도(위 항목 참고) "미검토"가 아니라 "검토완료"로
취급한다.

**가중치 튜닝 제약 (구조적 하드카운터 보호)**: 가산 모델이라 확실한
하드카운터도 다른 후보의 자잘한 시너지/맵 보너스 합산에 밀릴 수 있다.
이를 막기 위해 카운터 가중치 1건의 값은 **다른 모든 보너스 항목이 낼 수
있는 최댓값의 합(시너지 최대 개수 × 시너지 가중치 + 맵 가중치 최댓값)보다
항상 크게** 잡는다. 새 가중치를 조정할 때마다 이 부등식을 만족하는지
확인한다 — 별도 알고리즘 추가 없이 가중치 값만으로 하드카운터 우선순위를
보장한다.

### 데이터베이스 (SQLite)

| 테이블 | 컬럼 | 설명 |
|---|---|---|
| `heroes` | id, name, role, archetype, icon_url, archetype_category | 영웅 목록 (역할: 탱커/딜러/힐러). `archetype`은 목업 대조 후 추가된 컬럼 (예: "방벽 수문장") — 초안 단계에선 `tagline`으로 불렀으나 실제 구현에서 `archetype`으로 확정 |
| `maps` | id, name, mode, image_url | 맵 목록 (모드는 참고용 메타데이터). `image_url`(2026-09-14 추가)은 OverFast API에서 확보한 맵 스크린샷 URL. `data_richness`는 컬럼이 아니라 `map_hero_ratings` 등록 건수로 API 응답 시점에 계산 |
| `counter_relations` | hero_id, countered_hero_id, reason | hero_id가 countered_hero_id를 카운터함 |
| `synergy_relations` | hero_id, synergy_hero_id, reason | 두 영웅이 시너지가 좋음 |
| `map_hero_ratings` | map_id, hero_id, rating, reason | 맵에서 영웅의 강함/보통/약함 평가. "보통"도 검토완료 표시를 위해 명시적으로 행을 기록한다 (건너뛰지 않음) |
| `reviewed_neutral_pairs` | hero_id, other_hero_id, relation_type | 카운터/시너지 관계를 검토했으나 유의미한 관계가 없다고 판단된 쌍의 마커. "결측치 3단 상태" 절 참고 |
| `hero_notes` *(MVP 범위 밖으로 확정)* | — | 카운터/시너지/맵 관계로 설명 안 되는 자유 코멘터리(패치 트렌드, 매치업 경고 등)용으로 검토했으나 신규 테이블은 만들지 않기로 확정. 대신 `HeroRecommendation.notes` 필드만 스키마에 마련해두고 현재는 항상 빈 배열을 반환한다 (아래 API 명세 참고) |

시드 데이터는 개발 중 웹검색·커뮤니티 자료 조사 결과를 바탕으로 시딩
스크립트로 채워 넣는다. 처음부터 모든 조합을 완비하지 않고, 잘 알려진
관계 위주로 시작한다.

## 데이터 흐름

1. 사용자가 상대 팀 픽, 우리 팀 픽(+ 채울 빈 포지션), 맵을 입력하고
   추천 요청
2. 프론트가 `POST /api/recommendations` 호출
3. 백엔드가 빈 포지션에 해당하는 모든 영웅을 조회하고, 각 후보에 대해
   카운터/시너지/맵 점수를 합산
4. 상위 3~5개를 근거와 함께 정렬해 반환
5. 프론트가 순위 리스트 + 근거를 렌더링

## 에러 처리

| 상황 | 처리 |
|---|---|
| 빈 포지션 또는 맵 미선택 | 프론트 측 검증으로 요청 전에 안내 (둘 다 필수 입력) |
| 상대/우리 팀 픽을 하나도 입력하지 않음 | 요청은 허용하되, 맵 점수만 반영된 추천 반환 (카운터/시너지 근거 없음) |
| 카운터/시너지/맵 관계가 "검토완료-중립" | 해당 항목 점수 0 처리, 근거에 표시하지 않음 (전체 근거가 하나도 없으면 "일반적으로 무난한 영웅" 문구 표시) |
| 카운터/시너지 관계가 "미검토" | 해당 항목 점수 0 처리 + `data_gaps`에 "데이터 없음" 배지로 노출 ("결측치 3단 상태" 절 참고). **맵 차원은 미구현** — 맵 평가 데이터가 없으면(또는 "보통"이면) `data_gaps` 노출 없이 그냥 0점(중립)으로만 처리된다. 카운터/시너지만 이 3단 상태가 실제로 코드에 반영돼 있다 |
| 백엔드 오류 | 502 반환, 프론트는 "잠시 후 다시 시도해주세요" + 재시도 버튼 표시 |

## API 명세 (상세)

화면 목업(밴프준 보조 입력 폼 · 맵 선택 모달 · 추천 결과 화면 · 입력 검증 오류 상태)을
근거로 각 엔드포인트의 요청/응답 스키마와 상태 코드를 구체화한다. **이 섹션은 실제 구현
(`backend/app/models.py`, `backend/app/routers/`)과 1:1로 맞춰져 있고, 전체 24개
백엔드 테스트(`backend/tests/`)로 검증됐다.** 초안 단계에서 쓰던 필드명과 다른 부분은
"주의" 문구로 표시해뒀다.

### 엔드포인트 개요

| 메서드 | 경로 | 설명 | 요청 스키마 | 응답 스키마 | 상태 코드 |
|---|---|---|---|---|---|
| GET | `/api/heroes` | 영웅 목록 조회 (입력 폼 "영웅 추가" 목록용) | - | `Hero[]` | 200, 502 |
| GET | `/api/maps` | 맵 목록 조회 (맵 선택 모달, 모드별 그룹 표시) | - | `Map[]` | 200, 502 |
| GET | `/api/meta` | 시드 데이터 시즌/버전 정보 (헤더 배지용) | - | `Meta` | 200, 502 |
| POST | `/api/recommendations` | 빈 포지션 추천 영웅 순위 조회 | `RecommendationRequest` | `RecommendationResponse` | 200, 400, 422, 502 |

- **422**: `map_id`가 요청 본문에 아예 없을 때 (pydantic 검증 실패). `empty_position`은
  2026-09-14 변경으로 선택 필드가 돼서 빠져도 422를 유발하지 않는다(아래
  "빈 포지션 자동 판단" 참고). 목업의 입력 검증 오류 화면은 프론트에서 먼저
  막지만, 백엔드도 방어적으로 동일 검증을 한다.
- **400**: 요청 본문 형식은 맞지만 `enemy_heroes`/`our_heroes`/`map_id`에 DB에 없는
  id가 섞여 있을 때 (예: 오타, 삭제된 영웅 id). `empty_position`을 생략했는데
  `our_heroes`가 4명이 아니거나, 4명이어도 표준 조합(탱커1·딜러2·힐러2)으로
  설명되지 않는 구성(예: 탱커 2명, 또는 두 역할이 동시에 부족)일 때도 400.
- **502**: 예상 못 한 서버 오류. `BackendError.dc.html` 화면("잠시 후 다시
  시도해주세요" + 재시도 버튼)과 매칭.

### 빈 포지션 자동 판단 (2026-09-14 변경)

**배경**: 실사용 테스트에서 두 가지 문제가 지적됐다 — (1) `our_heroes`의 역할
구성에 아무 제약이 없어서 탱커 4명처럼 비현실적인 조합도 그대로 받아들여졌고,
(2) 급박한 실전 밴프준 상황에서 "우리 팀 픽"과 별개로 "빈 포지션"을 매번
수동으로 또 선택해야 하는 게 불필요한 단계였다. 사용자는 이미 자기 팀에 어떤
역할이 빠졌는지 알고 있으므로(그게 바로 자신이 채울 자리이므로), 그 정보를
다시 입력받을 필요가 없다.

**해결**: `empty_position`을 필수에서 선택으로 바꿨다.
- 값을 명시하면 기존과 동일하게 그 포지션 기준으로 추천한다(하위 호환 —
  `our_heroes`가 4명 미만인 "이른 단계" 시나리오에서 여전히 유용).
- 생략하면 `our_heroes`가 **정확히 4명**이어야 하고, 그 4명의 role을
  `config.TEAM_ROLE_COMPOSITION`(탱커1·딜러2·힐러2, 표준 5인 조합) 기준과
  비교해 정확히 한 역할만 1명 부족하면 그 역할을 빈 포지션으로 자동 채택한다
  (`backend/app/composition.py`의 `infer_empty_position`). 4명이 아니거나,
  조합이 표준으로 설명 안 되면(정원 초과, 또는 두 역할이 동시에 부족) 400으로
  막고 어떻게 고쳐야 하는지 안내한다.
- 프론트(`frontend/src/app/page.tsx`)는 이 변경에 맞춰 "빈 포지션" 수동 선택
  UI(`RoleSelectPanel`)를 완전히 없앴다 — "우리 팀 픽 (4명 모두)"만 채우면
  끝. 응답의 `empty_position` 필드(아래 참고)로 실제 적용된 포지션을 결과
  화면 상단에 표시한다.

**POST /api/recommendations — RecommendationResponse**
```
RecommendationResponse {
  empty_position: "tank" | "damage" | "support"   // 실제로 추천에 쓰인 포지션.
                                                    // 요청에서 생략됐으면 자동
                                                    // 판단된 값 (위 "빈 포지션
                                                    // 자동 판단" 참고).
  recommendations: [
    {
      hero_id: string
      hero_name: string
      role: "tank" | "damage" | "support"
      archetype: string          // Result.dc.html "지원 · 정찰 지원" 서브타이틀용
      icon_url: string           // 블리자드 CDN 초상화 URL. HeroOut.icon_url과 동일 값.
      archetype_category: string // 그룹 필터링용 상위 분류. HeroOut.archetype_category와 동일 값.
      total_score: int            // 카운터+시너지+맵 가중합 원점수. 상한 없음.
      percentage: int             // 0~100. percentage = round(50 + 50 * tanh(total_score / config.PERCENTAGE_SCALE)).
                                   // 초안/이전 버전의 하드 clamp(50 + total_score, 0, 100)를
                                   // 교체. 하드 clamp는 점수가 높은 후보끼리 100%로
                                   // 뭉개져 변별력이 사라지는 문제가 있었음 — tanh
                                   // 기반 완만한 포화 곡선으로 교체해 상한 근처에서도
                                   // 후보 간 차이가 (작게나마) 유지되도록 함.
                                   // PERCENTAGE_SCALE은 튜닝 상수 — 구현 시 실제
                                   // 가중치 범위에 맞춰 보정(예: 대표적인 "강한 픽"
                                   // 시나리오가 대략 90%대에 오도록).
                                   // 정규화는 "가중치 합 기준 절대 스케일"로 결정
                                   // (후보군 내 상대 정규화는 채택 안 함 — 상황이
                                   // 안 좋을 때도 1위가 인위적으로 높게 나오는 걸
                                   // 방지하기 위함).
      score_breakdown: { counter: int, synergy: int, map: int }
      reasons: string[]           // 근거 목록(자유 텍스트)
      is_must_pick: boolean       // percentage >= 90일 때 true
                                   // (config.MUST_PICK_PERCENTAGE_THRESHOLD로 확정)
      notes: string[]             // "최근 패치 이후 픽률 상승세" 같은 자유 코멘터리
                                   // 자리. hero_notes 테이블은 안 만들기로 확정해서
                                   // 현재는 항상 빈 배열 — 스키마만 먼저 맞춰둠.
      data_gaps: string[]         // "결측치 3단 상태" 절 참고. "미검토" 상태인
                                   // 항목만 여기 담김 (예: "상대 리퍼와의 관계
                                   // 미검토"). "검토완료-중립"은 여기 안 담기고
                                   // 조용히 0점 처리됨. 이 상태를 보여줄 목업은
                                   // 아직 없음 — 별도 화면 필요.
    }
  ]
  notice: string | null   // 상대/우리 팀 픽을 하나도 안 넣었을 때 등, 추천 근거가
                          // 제한적임을 알리는 안내 문구.
}
```
주의: 초안엔 응답 최상위에 `position` 필드가 없다고 봤었으나(요청의
`empty_position`을 프론트가 이미 들고 있어서 불필요한 중복이라 판단), 2026-09-14
변경으로 `empty_position`이 요청에서 생략 가능해지면서 프론트가 "실제로 어느
포지션이 적용됐는지" 알 방법이 응답 말고는 없어졌다 — 그래서 응답에
`empty_position`을 다시 추가했다.

    { "loc": ["body", "map_id"], "msg": "field required", "type": "value_error.missing" }

## 목업 대조 결과 — 스키마 보완 사항

목업 6장(메인 입력 폼 · 맵 선택 모달 · 추천 결과 · 중립 추천 결과 · 입력 검증
오류 · 백엔드 오류 상태)을 실제 구현된 응답 스키마와 대조해 빠진 필드를 찾아
백엔드(모델·리포지토리·라우터·스코어링·시드데이터·테스트)와 프론트엔드에
반영했다.

| 목업 요소 | 감사 결과 | 조치 |
|---|---|---|
| 영웅/추천 결과의 역할 세부 서브타이틀 ("지원 · 정찰 지원", "돌격 · 방벽 수문장") | 없음 (`heroes` 테이블엔 role만 존재) | `Hero.archetype`/`HeroRecommendation.archetype` 필드 추가, `heroes` 테이블에 `archetype` 컬럼 추가 + 15개 영웅 전체에 값 채움 |
| 추천 결과 1위의 "필수픽" 배지 | 없음 | `HeroRecommendation.is_must_pick` 필드 추가. 판정 기준은 "1위면 무조건"이 아니라 `percentage >= 90`(임계치, `config.MUST_PICK_PERCENTAGE_THRESHOLD`)으로 확정 — 1위라도 점수가 낮으면 배지 없음 |
| 근거 중 "최근 패치 이후 픽률 상승세" 같은, 카운터/시너지/맵 관계로 설명 안 되는 자유 코멘터리 | 없음 | `HeroRecommendation.notes: string[]` 필드 추가. 신규 `hero_notes` 테이블은 MVP 범위 밖으로 확정(큐레이션 비용 대비 우선순위 낮음) — 현재는 항상 빈 배열, 스키마만 준비 |
| 맵 선택 모달의 "데이터 풍부" / "데이터 보강 중" 그룹 배지 | 없음 | `Map.data_richness` 필드 추가(저장값 아닌 계산값 — `map_hero_ratings` 등록 건수 기준). 프론트는 그룹 내 최소값 기준으로 배지 표시 |
| 헤더의 "시즌 4 시드 데이터 · v0.3" 배지 | 없음 | `GET /api/meta` 엔드포인트 신규 추가 (`config.SEED_SEASON`/`SEED_DATA_VERSION` 상수 반환) |

### 이전 "미해결 항목" — 해결 완료

1. **점수 정규화 방식** → `percentage = round(50 + 50 * tanh(total_score / config.PERCENTAGE_SCALE))`로
   확정 (가중치 합 기준 절대 스케일 — 후보군 내 상대 정규화 방식은 채택하지 않음).
   `config.PERCENTAGE_BASELINE = 50`. (2026-09-08: 하드 clamp에서 tanh 기반 완만한
   포화 곡선으로 교체 — 아래 "스코어링 개선 검토" 참고)
2. **"필수픽" 판정 기준** → 순위(1위)가 아니라 절대 점수 기준.
   `percentage >= config.MUST_PICK_PERCENTAGE_THRESHOLD(90)`이면 true. 같은 요청에
   1위가 여러 명이거나, 1위인데도 90% 미만이면 배지 없음 — `test_is_must_pick_when_percentage_reaches_threshold`로 검증.
3. **패치 트렌드 / 매치업 경고성 근거** → 신규 `hero_notes` 테이블은 만들지 않기로
   확정(MVP 범위 밖, 향후 확장 항목으로 이동). 대신 `HeroRecommendation.notes`
   필드만 스키마에 마련해두고 현재는 항상 빈 배열 — 나중에 큐레이션 데이터가
   생기면 채워 넣기만 하면 되도록 응답 스키마와 프론트 렌더링(점선 테두리 태그)은
   이미 준비돼 있다.

## 스코어링 개선 검토 (2026-09-08)

목업 구현 이후 스코어링 로직을 다시 검토해 아래 4가지 개선 항목을
확정했다. 우선순위 순으로 정리한다 (룰 엔진/통계 기반 같은 아키텍처
확장은 이 4가지가 정리된 뒤에 재검토 — "보류한 대안" 참고).

| 우선순위 | 항목 | 상태 | 조치 |
|---|---|---|---|
| 1 | 결측치 3단 상태 | **구현 완료 (2026-09-08)** | "결측치 3단 상태" 절 참고. `reviewed_neutral_pairs` 테이블·`data_gaps` 필드가 `backend/app/scoring.py`·`repository.py`·DB 마이그레이션(`seed_db.py`)·프론트에 코드로 반영됨, 테스트로도 검증됨(`tests/test_scoring.py`/`tests/test_api.py`/`tests/test_repository.py`). **단, 카운터·시너지 두 차원만 구현됐고 맵 차원은 아직 미구현** — 위 "결측치 3단 상태" 절의 "구현 범위 관련 주의" 참고. 프론트의 `data_gaps` 배지 노출 볼륨(UX)은 별도 검토 항목으로 보류 중 |
| 2 | `percentage` 라벨링 오해 방지 | **구현 완료** | "%" 표시가 실제 승률처럼 오해될 수 있어, 프론트 표시 문구를 "OO%"가 아니라 **"추천 지수 OO"**로 변경(퍼센트 기호 제거) — `frontend/src/components/ResultsPanel.tsx`에 반영됨. API 필드명(`percentage`)과 0~100 범위는 유지 — 이미 구현된 코드/테스트와의 불필요한 churn 방지. 향후 통계 기반(실측 승률) 데이터가 섞이면 그건 별도로 "실측 승률 OO%" 라벨을 붙여 명확히 구분 |
| 2 | `percentage` 포화(clamp) 문제 | **구현 완료** | 하드 clamp → tanh 기반 완만한 포화 곡선으로 교체 (스키마 상세의 `percentage` 필드 주석 참고) — `backend/app/scoring.py`의 `ScoredHero.percentage`, `backend/app/config.py`의 `PERCENTAGE_SCALE`에 반영되고 `tests/test_scoring.py`로 검증됨. 순위 정렬 자체는 `total_score` 기준이라 원래도 깨지지 않았지만, 화면에 같은 숫자가 여러 개 뜨는 변별력 문제를 완화 |
| 3 | 하드카운터가 다른 점수에 상쇄되는 문제 | **구현 완료** | 새 메커니즘 없이 가중치 값으로 해결 — "점수 계산 로직"의 "가중치 튜닝 제약" 참고. `backend/app/config.py`에서 `WEIGHT_COUNTER(60) > 4*WEIGHT_SYNERGY + WEIGHT_MAP_STRONG(55)`가 되도록 가중치 상수를 조정했고, 이 부등식 자체와 실제 랭킹 결과를 `tests/test_scoring.py`(`test_weight_counter_exceeds_max_synergy_plus_map_strong_invariant`, `test_single_counter_outranks_max_synergy_and_strong_map_candidate`)로 고정 검증함 |
| 4 | 필수픽 배지 임계치(`MUST_PICK_PERCENTAGE_THRESHOLD = 90`) 검증 | **검증 완료 (2026-09-08)** | `backend/scripts/audit_must_pick_distribution.py`로 실제 시드 데이터 기준 분포 확인. 카운터 단독 31건 중 필수픽 발동 0건(0.0%, percentage 전부 88), 카운터+시너지 결합 7건 중 7건(100.0%, percentage 전부 91). 임계치를 90으로 유지함 — 카운터 단독(88%)은 전혀 발동하지 않고 카운터+시너지 결합(91%)은 전부 발동해, "신호 하나만으로는 부족하고 두 신호가 겹쳐야 필수픽" 설계 의도와 정확히 일치하는 경계선이 90 부근에 형성됨(참고: 시너지 단독 15건은 전부 58%로 역시 0건 발동). **주의**: 이 분포 자체가 현재 시드 데이터에서 카운터/시너지 관계 row마다 가중치가 전부 동일(카운터는 항상 WEIGHT_COUNTER, 시너지는 항상 WEIGHT_SYNERGY)해서 구조적으로 단순하게 나온 것 — 그룹별로 값이 하나로 수렴하는 건 "관계 강도에 따른 가중치 분산"이 아직 없기 때문이며, 임계치 90 유지 결론 자체를 무효화하진 않지만 이 숫자들을 "다양한 시나리오의 자연스러운 분포"로 과대 해석하면 안 됨 |

가장 중요한 한 가지만 꼽으면: 아키텍처 논쟁보다 **1번(결측치 편향) 구현**이
우선이다 — 지금 스펙 그대로 서비스를 내놔도 신뢰도에 가장 크게 흠집을
낼 지점이기 때문.

## UI 리디자인 — 결과 카드 · 영웅 선택 그리드 (2026-09-08)

사용자 피드백("영웅 이미지가 있으면 좋겠다", "우리 팀 픽 자동 판별", "전체적인
디자인 개선") 중 이번 라운드는 **결과 카드**와 **영웅 선택 그리드** 두 화면의
리디자인만 다룬다. 나머지 화면(에러 화면, 헤더/네비게이션)과 "우리 팀 픽 기반
빈 포지션 자동 판별"은 범위 밖 — 별도로 다룬다.

owtics.gg(다크 모드, 원형 영웅 아이콘, 데이터 중심 카드)를 무드 참고용으로
검토했으나, 그쪽은 통계 대시보드라 페이지 구조까지 그대로 가져오지는 않는다.
기존 다크+오렌지 팔레트(`--bg`, `--accent` 등)는 유지한다.

### 영웅 이미지

**출처**: OverFast API(`https://overfast-api.tekrop.fr/heroes`)의 `portrait`
필드가 블리자드 공식 CDN(`d15f34w2p8l1cc.cloudfront.net`)을 직접 가리킨다.
개발 단계에서 이 엔드포인트를 한 번 조회해 영웅별 URL을 시드 데이터에
저장해두고, 런타임에는 그 URL을 그대로 `<img>`로 핫링크한다 — "런타임에는
외부 API를 호출하지 않는다"는 기존 원칙을 그대로 지킨다.

**주의**: OverFast의 `key`(영웅 식별자)가 우리 `heroes.id`와 이름 표기가
다를 수 있다(예: 영문 slug 표기 차이). 시드 데이터를 채울 때 이름/역할 기준으로
수동 대조해 매핑해야 한다 — 실제 구현 단계에서 확인할 것.

**결과 카드(`ResultsPanel`)**: 후보 영웅마다 지름이 큰 원형 아이콘(64px) +
1위/필수픽에는 주황 강조 테두리. 시각 companion에서 A안으로 확정.

**영웅 선택 그리드(`HeroPickerPanel`)**: 작은 원형 아이콘(28px) + 이름을 같이
보여주는 칩 형태. 시각 companion에서 A안으로 확정.

**아이콘 없는 경우 폴백**: `icon_url`이 비어 있으면(마이그레이션 직후 등)
이미지 대신 이름 첫 글자를 넣은 단색 원(기존 이니셜 방식)으로 대체 표시한다.

### 아키타입 카테고리 (그룹 필터링용)

기존 `heroes.archetype` 필드(영웅마다 고유한 한 줄 설명, 예: "정찰 지원" —
결과 카드 서브타이틀용)는 그대로 둔다. **별도로** `archetype_category` 필드를
추가한다 — 여러 영웅이 공유하는 상위 분류로, 영웅 선택 그리드에서 역할 탭
안의 소제목으로 쓰인다.

카테고리 값은 블리자드 공식 체계를 그대로 쓴다 (역할별로 정해진 하위 집합만
유효):

| 역할 | 아키타입 카테고리 |
|---|---|
| 돌격(tank) | 개시자 / 투사 / 강건한 자 |
| 공격(damage) | 전문가 / 수색가 / 측면 공격가 / 명사수 |
| 지원(support) | 전술가 / 의무관 / 생존왕 |

역할과 카테고리 값이 항상 짝이 맞아야 하지만(예: 돌격 영웅은 "전술가"가 될
수 없음), `maps.mode`와 같은 기존 관례를 따라 DB에는 CHECK 제약 없이 TEXT로
저장하고 유효 값 목록은 이 표로만 문서화한다.

**현재 15명 로스터 배정** (실제 큐레이션 값 — `seed-data/heroes.json` 갱신 시
반영):

| 역할 | 카테고리 | 영웅 |
|---|---|---|
| 돌격 | 개시자 | 윈스턴, 디바 |
| 돌격 | 투사 | 오리사, 자리야 |
| 돌격 | 강건한 자 | 라인하르트 |
| 공격 | 측면 공격가 | 겐지, 트레이서 |
| 공격 | 명사수 | 위도우메이커, 소전 |
| 지원 | 전술가 | 아나, 루시우, 바티스트, 젠야타 |
| 지원 | 의무관 | 모이라, 키리코 |

(공격의 "전문가"/"수색가", 지원의 "생존왕"은 지금 로스터엔 해당 영웅이 없어
소제목이 아예 안 뜬다 — 로스터 확장 시 자연스럽게 채워짐. 빈 카테고리 소제목은
렌더링하지 않는다.)

### 영웅 선택 그리드 구조 변경

기존: 역할 탭 → 영웅 그리드 (평면).
변경: 역할 탭(라벨을 "탱커/딜러/힐러"에서 공식 용어 "돌격/공격/지원"으로 변경

시각 companion에서 레이아웃 구조(역할 탭 → 아키타입 소제목 → 영웅 칩)를
확정("O" 선택).

`heroes` 테이블에 컬럼 2개 추가:

| 컬럼 | 타입 | 설명 |

  - `POST /api/recommendations` 라우트 테스트 (정상 케이스, 입력 없는
    케이스, 데이터 없는 영웅 조합 케이스)
  - `GET /api/heroes`, `GET /api/maps` 라우트 테스트
- **프론트엔드**
  - 입력 폼 검증 컴포넌트 테스트 (빈 포지션/맵 필수 입력)
  - 결과 리스트 렌더링 컴포넌트 테스트 (목 데이터로 순위+근거 표시 확인)
- **수동 검증**
  - 실제로 잘 알려진 카운터 조합(예: 상대 겐지 → 윈스턴 추천)을
    입력해 결과가 합리적인지 확인
  - 데이터가 없는 낯선 조합을 입력했을 때 앱이 죽지 않고 중립적으로
    동작하는지 확인
