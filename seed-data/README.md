# 오버워치 밴프준 보조 — 시드 데이터 (v0)

스펙 문서(`오버워치 밴프준 영웅 추천 서비스 — MVP 설계`)의 DB 스키마를 그대로 따르는
시드 데이터 세트. 영웅·맵 로스터는 전체 영웅(54종, 도미나·독트린 등 2026년
신규 영웅 포함)과 6개 모드 맵(32개)까지 채웠고, 카운터/시너지/맵 평가
**관계 데이터**도 대부분의 영웅에 대해 최소 1건 이상 커버하도록 계속 넓혀가는
중이다 — 스펙의 "잘 알려진 관계 위주로 시작하고, 데이터가 없는 조합은 결측치
3단 상태로 처리" 방침대로, 아직 근거가 부족한 조합은 여전히 "미검토"로 표시된다.

## 포함 범위

- **영웅 54종** (`heroes.json`): 돌격 15 · 공격 24 · 지원 15. 각 영웅에는 `archetype`(역할 세부 서브타이틀, 예:
  "정찰 지원", "방벽 수문장")도 붙어있다 — Result.dc.html의 "지원 · 정찰 지원" 같은
  표시에 쓰는 필드. 추가로 `icon_url`(초상화 URL — 대부분 OverFast API/블리자드
  CDN, 신규 영웅 일부는 나무위키 등 대체 출처)과 `archetype_category`(그룹
  필터링용 상위 분류, 예: "의무관", "개시자" — 역할별로 정해진 하위 집합만 유효,
  OverFast API의 `subrole` 필드와 1:1 매핑)도 붙어있다.
- **맵 32종** (`maps.json`): 혼합 8 · 호위 8 · 점령 7 · 밀기 4 · 플래시포인트 3 ·
  격돌 2. 맵마다 큐레이션 밀도가 다르다 — 초기 8개 맵(혼합 3·호위 3·점령 2)이
  가장 두껍고, 나머지는 1건짜리부터 점점 채워나가는 중. `hanaoka`(하나오카)만
  레이아웃에 대한 확신이 부족해 아직 0건으로 남겨뒀다.
- **카운터 관계 155건** (`counter_relations.json`)
- **시너지 관계 82건** (`synergy_relations.json`)
- **맵×영웅 평가 108건** (`map_hero_ratings.json`, 강함/약함만 표기 — 평가가 없는
  조합은 스펙 방침대로 "보통(중립)"으로 취급하면 됨)
- **검토완료-중립 마커 48건** (`reviewed_neutral_pairs.json`) — "결측치 3단 상태"의
  "검토했으나 유의미한 관계 없음" 상태를 표시하는 테이블.

## 다국어(영어/일본어) 지원

`heroes.json`(`name_en`/`name_ja`/`archetype_en`/`archetype_ja`), `maps.json`
(`name_en`/`name_ja`), `counter_relations.json`/`synergy_relations.json`/
`map_hero_ratings.json`(각 `reason_en`/`reason_ja`)에 한국어 원본 옆에 영어/일본어
번역이 나란히 들어있다. 영웅 킷(스킬 이름 등)은 실제 오버워치 공식 로컬라이징
용어를 쓰도록 신경 썼고, 2025~2026년 신규 영웅처럼 공식 로컬라이징이 불확실한
경우는 메커니즘을 설명적으로 번역했지 지어내지 않았다(각 항목에 번역 결정 근거를
커밋 메시지에 남겨둠). `archetype_category`/`role`/`mode`처럼 그룹핑용 내부
식별자는 언어와 무관하게 항상 한국어 원본값 그대로이고, 화면 표시용 번역은
프론트엔드(`frontend/src/lib/i18n.ts`)가 별도 사전으로 담당한다.

새 카운터/시너지/맵 평가 데이터를 추가할 때는 `reason_en`/`reason_ja`도 같이
채워야 한다 — 비워두면 API가 조용히 한국어로 폴백하기 때문에(`seed_db.py`의
`with_i18n_defaults`), 당장 에러는 안 나지만 그 항목만 번역이 안 된 채로 남는다.

## 신규 영웅 큐레이션 시 유의할 점

2026년에 새로 추가된 영웅(해저드·안란·엠레·프레야·시온·시에라·벤데타·제트팩 캣·
미즈키·주노·도미나·독트린 등)은 큐레이션 담당(사람 또는 세션)의 학습 데이터
시점보다 나중에 나온 경우가 많다. 이럴 땐 감으로 킷을 추측해서 근거를 쓰지 말고,
반드시 먼저 신뢰할 수 있는 출처(공식 블리자드 페이지, 나무위키, Overwatch Wiki
등 2곳 이상 교차 확인)로 실제 스킬/쿨타임/메커니즘을 조사한 뒤에 그 사실에
근거해서 카운터/시너지/맵 평가 문구를 작성할 것 — 이 저장소의 다른 근거 문구들도
전부 "이 스킬이 저 스킬을 이렇게 무력화한다"는 구체적 상호작용 논리로 되어 있고,
막연한 "커뮤니티 평가"나 티어리스트 순위를 그대로 베끼는 방식이 아니다.
- **도미나**: 2026-09-16 기준 킷 조사 완료, 카운터/맵 평가 큐레이션 반영됨.
- **독트린**: 2026-10-06 출시 예정인 프리릴리즈 영웅이라 확인된 킷 정보가
  제한적임 — 확인된 만큼만(카운터 2건·시너지 2건) 반영했고, 맵 평가는 아직
  0건으로 남겨뒀다. 정식 출시 후 킷이 확정되면 더 채울 것.

## 데이터 성격 (중요)

- 스킬 상호작용(반사, CC기, 무적기, 기동력 등) 기반의 **일반적으로 잘 알려진
  관계** 위주로 작성했다. 실시간 승률 통계를 크롤링한 게 아니라 사람이 손으로
  큐레이션한 "MVP 시드"이므로, 실제 서비스에 쓰기 전에 본인 판단으로 다시 검수하는
  걸 권장.
- `counter_relations`/`synergy_relations`는 한 방향으로만 저장돼 있다
  (예: `zarya→genji`는 있지만 `genji→zarya`는 없음). 서비스 로직에서 "이 영웅이
  상대 팀 누군가를 카운터하는가"를 물을 때는 `hero_id = 후보영웅`,
  `countered_hero_id = 상대영웅` 방향으로만 조회하면 되므로 스펙의 점수 계산
  로직과 그대로 맞는다.
- `map_hero_ratings.rating`은 스펙 원문 그대로 `강함/보통/약함` 3단계 체계를
  쓰되, 데이터가 있는 것만 `강함`/`약함`으로 넣고 나머지는 아예 행을 만들지
  않았다 (= 조회 시 없으면 중립 처리). **주의**: 스펙의 "결측치 3단 상태"
  (미검토/검토완료-중립/검토완료-값있음)는 카운터/시너지 관계에만 실제로
  구현돼 있다 — `data_gaps` API 필드는 카운터/시너지 미검토만 노출하고, 맵
  평가는 여기 적힌 대로 "없으면 그냥 중립"인 기존 방식 그대로다(미검토와
  검토완료-중립을 구분하지 않음). 맵 차원까지 3단 상태로 확장하는 건 아직
  향후 과제.

## 사용법

```bash
python3 seed_db.py            # overwatch.db 생성
python3 seed_db.py mydb.db    # 경로 지정도 가능
```

FastAPI 쪽에서는 이 스크립트를 그대로 시딩 스크립트로 쓰거나, 앱 시작 시
`heroes.json` 등을 직접 읽어 SQLAlchemy 모델에 넣어도 된다. 스키마는
`seed_db.py` 안의 `SCHEMA` 상수에 있고 스펙 문서의 테이블 정의와 1:1로 대응한다.

> **⚠️ 중요 — 스키마를 바꿨으면 반드시 커밋된 DB 파일도 다시 시딩할 것**
>
> `heroes.json` 등 JSON 데이터나 `seed_db.py`의 `SCHEMA`(컬럼 추가/변경)를
> 고쳤다면, 그걸로 끝이 아니다. **`git`에 커밋돼 있는 `overwatch.db` 자체가
> 여전히 옛 스키마다** — `seed_db.py`를 임시 파일에 대고 돌려서 검증만 하고
> 정작 저장소에 들어있는 `overwatch.db`는 갱신을 안 하면, 새로 체크아웃한
> 사람/CI는 예전 스키마의 DB를 그대로 받게 되고 `no such column` 같은 500
> 에러가 난다 (실제로 이 프로젝트에서 한 번 이렇게 터진 적 있음 — Critical
> 버그로 별도 수정됨).
>
> 스키마나 시드 데이터를 바꿀 때마다 반드시:
> ```bash
> cd seed-data
> python3 seed_db.py overwatch.db   # 커밋된 파일 경로를 직접 지정 — 임시 파일 아님!
> git add overwatch.db
> git commit   # 갱신된 DB 바이너리를 커밋에 포함시킬 것
> ```
> `seed_db.py`는 `ALTER TABLE ... IF NOT EXISTS` 패턴으로 기존 행을 보존하면서
> 마이그레이션하므로 안전하다. 하지만 이 커맨드를 실행하고 결과를 커밋하는 걸
> "깜빡"하면 스키마 변경 자체가 무의미해진다 — 절대 건너뛰지 말 것.

**주의(macOS + 클라우드 브릿지 환경)**: `seed-data/`가 클라우드 세션의 연결된
폴더(mnt) 안에 있으면 SQLite가 그 경로에서 직접 쓰기 작업(ALTER TABLE 등)을 할 때
`disk I/O error`가 날 수 있다. 이럴 땐 임시로 로컬 경로에 만들고(`python3 seed_db.py
/tmp/overwatch.db`) 완성된 파일만 `cp`로 옮겨 넣으면 된다 — 로컬에서 직접 만든
DB 파일 자체를 읽고 쓰는 건 문제 없다.

## 다음에 늘릴 때

- 영웅·맵 카탈로그(선택 목록) 자체는 전체 로스터로 다 채워졌고, 관계 데이터도
  대부분의 영웅이 카운터/시너지 각 1건 이상은 갖도록 넓혀놨다. 남은 건 **맵
  평가 커버리지**(현재 1건짜리 맵이 많음)와 **각 영웅당 근거 개수를 더 두껍게**
  만드는 것 — 특히 `hanaoka`(하나오카)는 아직 0건.
- 독트린은 2026-10-06 정식 출시 예정이라 맵 평가는 아직 비워뒀다 — 출시 후
  실제 플레이 정보가 쌓이면 채울 것.
- `neon_junction`(네온 교차로)은 OverFast API 스크린샷이 계속 404라서(2026-09-15),
  사용자가 직접 캡처한 스크린샷을 `frontend/public/maps/neon_junction.png`로
  대신 넣었다 — `image_url`이 다른 맵들과 달리 외부 URL이 아니라 상대 경로
  (`/maps/neon_junction.png`)다. OverFast가 나중에 캐싱하면 다시 외부 URL로
  되돌려도 무방.
- `/topics` 프로젝트에 저장해둔 `오버워치-메타-노트.md`(아이치 티어리스트 요약)에
  "왜 밴당하는가"를 카운터형/짜증유발형/순수스탯형으로 구분한 관점이 있으니,
  `reason` 문구를 쓸 때 참고하면 좋다.
